# Repository Structure v10

Status: **canonical** — 2026-09-13.

This is a deliberate breaking redesign from v9: new canonical work no longer uses `SOURCE`, `TARGET`, `COMPARE`, or `REFERENCE` as ownership branches.

v10 replaces the v8/v9 `SOURCE/TARGET` ownership vocabulary with a release-centric model. The same coordinate IDs are used in both `Sakurai` and `Tsubaki`; repository role determines which artifact classes live at that coordinate.

## 1. Canonical roots

```text
GEN-XX/
CROSS-GEN/
INFRA/
```

No new top-level generation aliases are allowed. Existing legacy roots remain read-only until migrated or quarantined.

## 2. Game ownership

```text
GEN-XX/<GAME-ID>/
├── RELEASES/
├── PROJECTS/
├── COMPARES/
├── REFERENCES/
└── SHARED/
```

These names describe ownership, not file type. Empty placeholders are not required.

## 3. RELEASES grammar

```text
GEN-XX/<GAME-ID>/RELEASES/<PLATFORM-ID>/<PACKAGE-KIND>/<RELEASE-ID>/
```

A release is a conceptual official software release/build identity. An exact ROM image is a dump observation nested below that release.

```text
<RELEASE-ID>/
└── DUMPS/<DUMP-ID>/
```

`DUMP-ID` must be content-addressed. Current rule: `DUMP-SHA256-` plus the first 16 uppercase hex characters of the full SHA-256; the full hash is always stored in the observation manifest.

For platforms with a stable technical game/build code, that code is the preferred release-ID stem. Example: `BPRE-HV1`, `BPEJ-HV0`, `AAUK-HV0`. If the ROM header has no stable code, use a deterministic market/language/header-version fallback such as `JP-JA-HV1`; never invent a fake product code.

Language, market, region, revision, hash, title, and checksum remain explicit manifest fields. They are not turned into arbitrary extra directory levels.

## 4. Sakurai responsibility

`Sakurai` is the knowledge/control plane. Under a release coordinate it owns:

```text
RELEASE.json
DUMPS/<DUMP-ID>/OBSERVATION.json
ANALYSIS/
TABLES/
REPORTS/
VERIFICATION/
TOOLS/
```

Sakurai is authoritative for identity, provenance, research, reverse-engineering notes, schemas, mapping tables, comparisons, specifications, analysis tools, and verification evidence.

## 5. Tsubaki responsibility

`Tsubaki` is the production/data plane. At the same release coordinate it owns:

```text
SOURCE.ref.json
DUMPS/<DUMP-ID>/EXTRACTION.plan.json
CATALOGS/
ASSETS/
NORMALIZED/
CONVERTED/
IMPLEMENTATION/
PATCHES/
BUILD/
VERIFICATION/
TOOLS/
```

Tsubaki is authoritative for ROM-derived working assets, normalized assets, conversions, implementation data, patches, build recipes, and reproducible production outputs. ROM images themselves remain excluded from `BUILD/`.

## 6. PROJECTS

Single-game work:

```text
GEN-XX/<GAME-ID>/PROJECTS/<PROJECT-ID>/
```

Same-generation work intentionally spanning games:

```text
GEN-XX/PROJECTS/<PROJECT-ID>/
```

Cross-generation work:

```text
CROSS-GEN/PROJECTS/<PROJECT-ID>/
```

Every project manifest must pin its input release coordinate(s) and, when byte-exact behavior matters, the exact dump ID(s).

## 7. COMPARES / REFERENCES / SHARED

Same-game comparison:

```text
GEN-XX/<GAME-ID>/COMPARES/<COMPARE-ID>/
```

Same-generation cross-game comparison:

```text
GEN-XX/COMPARES/<COMPARE-ID>/
```

Cross-generation comparison:

```text
CROSS-GEN/COMPARES/<COMPARE-ID>/
```

`REFERENCES` contains external/secondary material and never overrides facts directly observed from software. `SHARED` is only for genuinely release-independent reusable resources. Byte-identical release-owned content stays attached to its release and equality is recorded by hash/catalog.

## 8. Pair invariant

Both repositories use identical values for generation ID, game ID, platform ID, package kind, release ID, dump ID, project ID, compare ID, and reference/resource IDs.

The path through the semantic coordinate is therefore the same in both repositories. What differs is the artifact class stored under that coordinate.

## 9. ROM binary exclusion

Original ROM images and modified/playable ROM images are never committed. This includes GB/GBC/GBA/NDS and equivalent cartridge/disc/install images. Hashes, manifests, scripts, patches, extracted/normalized assets, build recipes, logs, reports, and verification data are tracked.

## 10. Forbidden new canonical labels

Do not create new canonical paths using ambiguous or retired ownership labels such as:

```text
SOURCE
TARGET
COMPARE
REFERENCE
MULTI
ALL
REV-ALL
ALL-RELEASES
MULTI-REGION
MISC
OTHER
GENERAL
REV-UNKNOWN
MIGRATED
```

Legacy occurrences are migration inputs, not templates for new work.

## 11. Examples

```text
GEN-02/GOLD/RELEASES/GBC/CART/AAUK-HV0/
GEN-03/FIRERED/RELEASES/GBA/CART/BPRE-HV1/
GEN-03/LEAFGREEN/PROJECTS/PAST-PARADOX-001-386/
GEN-02/SILVER/PROJECTS/KR-MODERNIZATION/
GEN-03/COMPARES/RS-E-ENGINE/
CROSS-GEN/PROJECTS/NATIONAL-DEX-INTEGRATION/
```
