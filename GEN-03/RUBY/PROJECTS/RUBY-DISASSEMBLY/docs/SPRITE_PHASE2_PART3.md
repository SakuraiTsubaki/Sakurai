# Sprite engine reconstruction — Phase 2, Part 3

Part 3 continues exactly at `SetOamMatrixRotationScaling`, the boundary left by Part 2, and maps the sprite sheet/tile allocator plus palette manager through `FreeSpritePaletteByTag`.

## Coverage

- 13 verified Pokémon Ruby ROM targets.
- 2 verified function-layout families: Japanese and international/debug.
- 293 target/function fingerprint records are reproducibly generated by the analyzer.
- International/debug block: `0x508` / 1288 bytes, 23 functions.
- Japanese block: `0x3FC` / 1020 bytes, 17 functions.
- Next boundary in every target: `SetSubspriteTables`.

The exact layouts are stored in `symbols/sprite_part3_layouts.csv`; per-target bases/end offsets and whole-region SHA-1 fingerprints are in `symbols/sprite_part3_targets.csv`. `tools/analyze_sprite_part3.py` validates the source ROMs and can generate `symbols/sprite_part3_fingerprints.csv` only after whole-ROM SHA-1 verification.

## Important Japanese/international split

The first three functions are present in both layouts:

1. `SetOamMatrixRotationScaling`
2. `LoadSpriteSheet`
3. `LoadSpriteSheets`

The international/debug object then contains six extra sheet helpers that are not present at this position in the Japanese Rev 0 object:

- `AllocTilesForSpriteSheet`
- `AllocTilesForSpriteSheets`
- `LoadTilesForSpriteSheet`
- `LoadTilesForSpriteSheets`
- `RequestSpriteSheetCopy`
- `LoadSpriteSheetDeferred`

After accounting for those functions, both layouts continue with the same resource-management semantics: freeing/querying sprite tile ranges, internal tag lookup/range allocation, then palette allocation/loading/freeing.

This is a ROM-derived layout observation. Public `pret/pokeruby` source was used to cross-check function semantics/names; addresses, sizes and hashes were taken from the verified local ROM set.
